## 初次只读检查发现的缺口（本日后续处理见下文）

1. `service/core/sales_source_parser.py:20` 的 Excel 表头别名尚不包含客户料号/物资编号/图号等专用字段；`:91` 的文字解析只接受两/三列显式商品编码。Excel 无 ERP 编码的记录保留待核对，但不自动匹配。
2. `service/core/sales_document_pipeline.py:121` 保留 PDF/OCR 行及出处，再将行交给同一 `parse_text`，尚无跨行表格重建、自然语言需求提取或客户料号候选。
3. `service/core/sales_assistant.py:519` 仅按精确 `records.sku` 查当前账套、仓库、SKU、单位身份；没有读旧匹配库。`sales_source_review.py` 是“已选商品是否与原文冲突”的核查器，不是商品候选搜索。
4. `/api/v2/inventory` 可以只读查询当前目录；`/api/v2/order-history/lines` 只支持商品编码/单号查询，目前归档为 0 且由管理员访问。没有客户料号/同客户历史的员工只读候选接口。
5. 旧 `match_order_items.py` 有属性解析、候选排序与理由；旧 `process_quote_to_sales_import.py:544` 有料号历史查询、`:633` 有历史需求匹配。不过存在固定 `%振华%` 范围、占比 98% 当作唯一、没有同客户命中时改用全局历史等行为，均不能原样接入。旧材质/表面同义规则、标准关系和等级替代也需要逐条核实，不能通过宽泛规范化合并商品身份。
6. `service/core/importers.py:141` 的旧订单导入只接受 `FIELDS` 对应“系统备注”；旧销售表使用 `SALES_ORDER_FIELD_ALIASES` 的五类字段，尚未保留历史“摘要/旧备注”。不能通过这个导入器把 55,169 行历史直接灌入当前未完成订单快照；需要独立历史参考迁移，保留 `raw_remark` 和当前 `summary` 的显式字段映射。

3. 新增会话内只读候选查询：服务端根据不可变客户身份、来源行、当前数据版本及参考资料版本查询，不接受客户端任意扩展客户范围；返回最多 5 个候选、逐项差异、依据与出处。没有明示规则时不跨客户，603 组多编码不能按 98% 频率视为唯一。

5. 员工选择候选后沿用当前服务端来源确认哈希、草稿版本、数据版本和幂等保护；商品变化使确认失效。最终确认仍冻结客户、人员、税价、单位、仓库、交期、摘要、明细及人工说明；提取或匹配不能自动提交。
