# UL 随行 N150 部署、备份与恢复说明（App 0.3.0 / 镜像 0.4.0）

更新：2026-09-30。

本文依据当前工作区的 `Dockerfile`、`compose.yaml`、`service/backup.py` 和 `deploy/` 编写，说明可由代码确认的部署与恢复行为。本文不是 N150 线上验收记录；执行前仍须核对目标机的实际路径、镜像、挂载、磁盘余量和任务状态。

## 1. 版本与运行边界

| 项目 | 当前发布标识 |
| --- | --- |
| Android App | `0.3.0-dev`，`versionCode=9` |
| Android applicationId | `com.ul.workbench.dev` |
| 后端 Docker 镜像 | `ul-workbench:0.4.0` |
| 后端健康信息中的服务版本 | `1.4.0` |
| 数据库 | N150 本地磁盘上的 SQLite，WAL 模式 |
| 容器进程 | UID/GID `10001:10001`，只读根文件系统 |

`compose.yaml` 将业务数据目录挂载到 `/app/service/runtime/data`，将 APK 发布目录只读挂载到 `/app/releases`。数据库必须留在 N150 业务虚拟机的本地磁盘，不能直接放在 SMB/NAS 共享目录运行；NAS 只保存一致性加密备份。

默认配置为：

- `UL_LOGISTICS_WRITE_ENABLED=0`，物流写入关闭。
- 后端端口默认只绑定 `127.0.0.1:5191`；目标机若使用其他绑定地址，应保留现网 `.env` 中已经核准的值。
- 容器根文件系统只读，临时目录使用 64 MiB `tmpfs`。
- 每个容器最多使用 2 CPU、1536 MiB 内存和 128 个进程。
- 业务数据更新由 App 中的“更新订单”或受控 API 请求手动发起。

仓库中虽然提供 `ul-auto-sync.timer` 和 `ul-full-reconcile.timer`，本版本的业务边界仍是**不启用这两个定时器**。每日备份、证书续期及 ERP Token 维护可以自动执行；它们不等于自动同步订单或自动写入物流。

## 2. 目录与需要保留的内容

目标机工作目录按现有脚本约定为 `/opt/ul-workbench`。systemd 服务和备份脚本使用这个路径，升级时不要随意改名。

必须保留：

- `service/runtime/data/`：SQLite、WAL/SHM、会话、更新任务、物流成功缓存、逐笔请求、打印状态、库存台账、ERP 授权和服务端密码哈希。
- `releases/`：当前及旧 APK、`current.json`。发布新 APK 时先放 APK，最后原子替换 `current.json`。
- 现网 `.env`：包含目标机自己的数据目录、发布目录和绑定地址等配置。
- `/etc/ul-workbench-backup.env`：NAS 挂载点、备份目录和非默认数据目录。
- 独立备份密钥：它不在加密备份包中，必须在另一处受限介质保存。
- 现网 systemd、反向代理、证书同步和防火墙配置。
- 升级前的旧镜像、旧 compose/source 副本和对应校验信息，直到新版本稳定且恢复演练完成。

部署包和源码传输必须排除：

- `runtime/` 与开发机的 `service/runtime/`。
- `.env`、任何密钥、keystore、授权文件和本地凭据。
- `.git/`、`.gradle/`、`.kotlin/`、`.pytest_cache/`、`__pycache__/`。
- `app/build/`、临时输出、日志和本地工具链缓存。

`.dockerignore` 会保护 Docker 构建上下文，但不会保护 `rsync`、`tar` 或手工复制。不得把整个开发工作区直接复制到 N150，也不得在没有上述排除项时运行 `rsync --delete`。数据目录和发布目录位于工作树下，无排除的删除同步会使恢复变困难。

## 3. 最安全的 0.4.0 镜像更新顺序

### 3.1 升级前冻结证据

在不改动业务数据的前提下记录：

- 当前 compose 和 `.env` 的校验值。
- 当前运行镜像的 ID、标签及容器健康状态。
- 当前 `UL_DATA_DIR`、`UL_RELEASE_DIR` 和备份任务实际使用的目录。
- 当前启用的 systemd timers；确认业务自动刷新和完整核对 timers 未启用。
- N150 本地磁盘及 NAS 备份目录余量。
- 是否存在 `queued/running` 更新任务、`sending/unknown` 物流请求、进行中的打印或调整批次。

先给现网镜像增加不会被 0.4.0 构建覆盖的回滚标签，并记录镜像 ID。不要只依赖 `latest` 或可变标签。

### 3.2 先备份，再构建

先手动启动一次现有备份服务，并检查服务以成功状态结束：

```bash
sudo systemctl start ul-backup.service
sudo systemctl status ul-backup.service --no-pager
```

备份脚本会拒绝未挂载的 NAS、拒绝把目标放到 NAS 挂载点以外，并在 NAS 上采用“临时文件 → `cmp` 比对 → 原子改名”的顺序。看到 systemd 成功只能证明脚本正常退出；正式升级前还应选取该备份做一次隔离恢复和 SQLite 完整性检查。

把脱敏后的运行源码放入临时 staging 目录，执行：

```bash
docker compose config
docker compose build workbench
docker image inspect ul-workbench:0.4.0
```

记录构建后的镜像 ID。基础镜像 `python:3.12-slim-bookworm` 和 Debian apt 包不是不可变 digest，未来重新构建不保证生成完全相同的镜像，因此应保留本次实际构建出的镜像。

预检应使用隔离数据目录，不能把生产数据挂给预检容器写入。预检至少覆盖：容器启动、`/livez`、SQLite 迁移、登录、只读订单/库存查询；它不能代替手机、打印机和真实业务验收。

### 3.3 切换容器

确认备份和新镜像后，再更新 `/opt/ul-workbench` 中的运行源码与 compose。必须保持生产数据目录、发布目录和 `.env` 不变。

```bash
cd /opt/ul-workbench
docker compose config
docker compose up -d --no-build workbench
docker compose ps
```

不要使用 `docker compose down -v`。切换后先检查容器健康、日志、登录和只读查询，再由管理员手动触发一次业务同步。物流写入仍保持关闭。

验证健康信息时应确认本次代码宣告的能力，包括库存台账、产品图片和整单打印状态。只有健康接口正常并不能证明 ERP 数据完整、图片可下载或标签实际出纸。

### 3.4 发布 0.3.0 APK

后端验证通过后再发布 APK：

1. 将 APK 以临时文件名复制到 `releases/`。
2. 核对 APK 的 SHA-256、ZIP 完整性、签名、applicationId 和 `versionCode`。
3. 将 APK 原子改名为 manifest 中的正式文件名。
4. 校验新的 `current.json` 后，最后原子替换 manifest。
5. 先在一台手机覆盖安装并验证，再安装第二台。

Android 通常不允许用较低 `versionCode` 覆盖较高版本。若 0.3.0 已安装，直接安装旧 APK 作为回滚可能失败；卸载又会清除手机中的草稿、设备 ID、会话和本地状态。需要 App 回滚时，应使用相同签名并采用更高 `versionCode` 构建回滚修复包。

## 4. SQLite 一致性加密备份

`service/backup.py` 不直接复制正在运行的 SQLite 文件。它使用 SQLite Backup API 在数据目录旁建立一致性副本，对副本执行 `PRAGMA integrity_check`，再打包和加密。因此 WAL 中已经提交的内容会被纳入同一个一致性快照。

备份包包含：

- `workbench.sqlite3`。
- `manifest.json`。
- 存在且不是符号链接时的 ERP 后端授权文件和管理员密码哈希。

备份包不包含：

- 32 字节备份密钥本身。
- `product-images/` 中的商品图片二进制缓存。
- APK、源码、compose、反向代理配置和 systemd 配置。

整个 ZIP 内容使用 AES-GCM 加密；输出文件以排他创建方式生成，权限为 `0600`，不会覆盖同名备份。明文 SQLite 暂存副本在数据目录本地创建，打包完成后由临时目录清理。

商品图片缓存不属于灾难恢复必需数据。SQLite 中保留图片元数据，缓存文件缺失时可从允许的 ERP 图片源按需重新下载。正常升级仍应保留整个数据目录，以避免不必要的重复下载。

不要用以下方式代替一致性备份：

- 在服务运行时直接 `cp workbench.sqlite3`。
- 只复制主数据库而遗漏 WAL 中已提交的数据。
- 把 SQLite 直接放在 NAS/SMB 上运行。
- 把备份密钥与加密包只保存在同一个位置。

## 5. 离线恢复

### 5.1 恢复前

1. 停止业务容器，确认没有进程继续访问原数据目录。
2. 保留原数据目录，只读记录其路径和时间；不要在原目录上覆盖恢复。
3. 选定备份包、与之匹配的独立密钥和一个**尚不存在**的新目标目录。
4. 保证恢复父目录位于 N150 本地磁盘，并有足够空间。

恢复函数会拒绝已存在的目标目录。下面是使用已有 0.4.0 镜像进行无网络离线恢复的示意；路径均为占位符，执行时按目标机实际目录替换：

```bash
cd /opt/ul-workbench
docker compose stop workbench

restore_parent=/opt/ul-recovery/<恢复批次>
backup_file=<加密备份包绝对路径>
backup_key_file=<独立备份密钥绝对路径>

sudo install -d -m 0700 "$restore_parent"
sudo docker run --rm --network none --read-only --user 0:0 \
  -v "$restore_parent:/restore" \
  -v "$backup_file:/input/backup.ulbackup:ro" \
  -v "$backup_key_file:/input/backup.key:ro" \
  ul-workbench:0.4.0 \
  python backup.py restore \
    --runtime /restore/data \
    --file /input/backup.ulbackup \
    --key-file /input/backup.key

sudo chown -R 10001:10001 "$restore_parent/data"
sudo chmod 0700 "$restore_parent/data"
if [ -d "$restore_parent/data/secrets" ]; then
  sudo chmod 0700 "$restore_parent/data/secrets"
  sudo find "$restore_parent/data/secrets" -type f -exec chmod 0600 {} +
fi
```

该命令不访问网络，写入的只有新恢复目录。开始前必须确认 `restore_parent/data` 不存在；命令中的占位符不得原样执行。

### 5.2 恢复后的保护状态

恢复代码会执行 SQLite 完整性检查，并主动进入保护状态：

- 写入 `settings.restoration_hold=true`。
- 撤销全部后端登录会话，手机需要重新登录。
- `queued/running` 更新任务改为 `unknown`，阶段改为 `restored`。
- 正在 `sending` 的物流请求改为 `unknown`。
- `queued/running` 报损报溢批次改为 `unknown`，并禁止自动重试。
- `prepared/claimed` 打印任务改为 `unknown`。
- 整单打印状态中的 `reserved` 改为 `uncertain`；存在审计表时写入 `restored_during_print` 审计记录。

这些任务都进入**待核对**，不能因恢复成功而自动重放。尤其不能自动补打标签、重复提交报损报溢或再次写物流。

把新目录设置为 `UL_DATA_DIR` 前，应保留原数据目录，并同步更新 compose 使用的 `.env` 和 `/etc/ul-workbench-backup.env`；否则容器与定时备份可能指向不同数据目录。启动后先验证登录、查询、数据版本和待核对列表。

本版本没有对外提供自动解除 `restoration_hold` 的接口。管理员必须先逐笔核对备份时间之后可能发生的物流、调整和打印动作，再通过单独审核的离线维护操作解除暂停。不要为了恢复写入而直接删除 `unknown` 记录，也不要在运行中的数据库上临时执行未复核 SQL。

## 6. 回滚策略

### 6.1 仅回滚后端代码

若 0.4.0 切换后尚未发生新的同步、打印状态变化或业务写入，可先停止新容器，改回升级前记录的不可变镜像标签，再用：

```bash
docker compose up -d --no-build workbench
```

SQLite v4 迁移是增量迁移，但不能在未测试的情况下假定旧镜像兼容新数据库。切回前应使用隔离副本验证旧镜像能读取该数据库；若不能，采用“恢复到新目录”的数据回滚流程。

### 6.2 回滚数据库

一旦升级后出现新的同步、打印、调整或人工核对，恢复旧备份会丢失备份之后的本地记录。此时：

1. 停服并保留当前数据目录。
2. 将已验证的备份恢复到另一个新目录。
3. 切换 `UL_DATA_DIR`，保持 `restoration_hold`。
4. 对照 ERP、纸面标签、手机草稿和原数据目录，核对备份之后的所有动作。
5. 完成核对后再解除写入暂停。

不得直接覆盖现有数据库。原数据目录是追查备份之后行为的重要证据。

### 6.3 回滚 Android App

优先通过“后端先升级、单手机灰度、第二台后装”减少 App 回滚需求。若必须回滚业务行为，应在当前签名基础上制作更高 `versionCode` 的修复包；不要通过卸载 App 规避版本限制，除非已经单独导出并核对手机草稿。

## 7. 手动业务同步与物流边界

- 普通业务更新由 App 明确点击后创建持久化任务；关闭 App 不会中断 N150 上已开始的任务。
- 同一时间只处理一个更新任务；重复 UUID 返回原任务，不能用反复点击制造并行更新。
- `refresh` 和 `reconcile` 是只读 ERP 采集、计算及本地快照发布模式，不应由 systemd timer 自动启用。
- `inventory_subset` 只刷新指定商品的库存缓存，用于局域网报损报溢上传完成后的局部刷新；它不写物流，也不人工修改实物库存。
- 查询读取最后一次成功发布的 SQLite 快照。ERP 暂时不可用时，不应删除上一份可用数据。
- 物流写入默认关闭。只有显式将 `UL_LOGISTICS_WRITE_ENABLED` 设为 `1`、成功加载已验收 sender、任务模式允许写入且不存在 `restoration_hold` 时，代码才可能发起物流请求。
- 物流请求超时或中断会保留为 `unknown`，必须人工核对；不能自动重发。
- 恢复后的 `restoration_hold` 会阻止物流写入以及报损报溢新提交/重试，直到备份之后的操作全部核对。

Token 自动维护只维持后端授权有效，不会自动执行订单同步。备份 timer 也只制作备份，不会触发业务同步。

## 8. 上线与恢复验收清单

### 镜像切换后

- 容器处于 healthy，未出现连续重启。
- `/livez` 正常，登录后健康接口显示预期服务版本和能力。
- 订单、库存、库存台账和商品图片接口可读；图片失败不阻止业务快照发布。
- 物流写入能力仍显示关闭。
- 业务自动刷新和完整核对 timers 仍未启用。
- App 只在一台手机灰度，查询、扫码和打印状态符合预期后再扩展。

### 备份后

- systemd 备份服务成功结束。
- NAS 中不存在遗留的临时文件。
- 新备份不是零字节，权限受限。
- 使用匹配密钥恢复到隔离新目录成功，`PRAGMA integrity_check` 通过。
- 隔离恢复目录没有被业务容器误挂载。

### 恢复后

- 原数据目录保持不变，可供审计。
- 手机旧会话失效并重新登录。
- 恢复数据处于 `restoration_hold`。
- 物流、调整、打印和整单预留的未知状态逐笔核对，没有自动重放。
- compose 和备份 systemd 环境指向同一个新数据目录。
- 解除暂停前又制作一次一致性备份，并保留核对记录。

## 9. 当前说明的验证范围

本文中的备份内容、恢复状态转换、镜像配置和 timer 行为来自当前工作区代码。本文编写过程中没有连接 N150、没有执行线上备份或恢复、没有切换镜像，也没有验证线上 NAS 挂载、实际镜像 ID、反向代理或手机安装结果。正式操作必须把上述只读核对和隔离恢复演练作为上线前步骤。
