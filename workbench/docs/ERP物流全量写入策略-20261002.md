# ERP 物流全量写入策略

日期：2026-10-02

## 目标

App 每次手动点“更新订单”时，同一任务内处理全部合格的物流差异，不再以100张为上限分批。

“全部”指本次读取和计算后，相对成功缓存发生变化、字段完整且没有被业务安全规则阻断的订单。待核对请求、分配范围受影响、字段缺失或分类异常仍保持阻断，不会为了“全量”绕过原有安全检查。

## 配置

正式全量模式需要同时满足：

```dotenv
UL_LOGISTICS_WRITE_ENABLED=1
UL_LOGISTICS_WRITE_SCOPE=all
UL_LOGISTICS_WRITE_MAX_PER_JOB=0
UL_LOGISTICS_WRITE_ALLOWLIST=
```

`UL_LOGISTICS_WRITE_SCOPE=all` 是独立的显式授权。只打开传输开关、但没有设置范围时，后端仍拒绝写入。`all` 与非零上限或非空白名单同时出现时，服务启动直接报错，避免旧的100张上限让“全量”悄然变成部分写入。

小批量验证或维修时仍可使用：

```dotenv
UL_LOGISTICS_WRITE_ENABLED=1
UL_LOGISTICS_WRITE_SCOPE=bounded
UL_LOGISTICS_WRITE_MAX_PER_JOB=3
UL_LOGISTICS_WRITE_ALLOWLIST=ORDER#1,ORDER#2,ORDER#3
```

## 持久化和失败处理

- 全量或有限策略都在任务入队时冻结，服务重启或修改 `.env` 不会改变已入队任务的范围。
- 差异按完整订单号稳定排序后逐笔提交；只有明确成功才更新 `freight_cache`。
- 请求超时或断连仍记为 `unknown`，不自动重发。受该请求库存分配范围影响的后续订单继续保持阻断。
- 任务结果仍报告 `selected`、`deferred` 和 `unchanged`。全量模式不会因数量上限产生 `deferred`；业务阻断会单独报告。

## 部署前检查

1. 确认没有排队或执行中的旧任务。旧任务保留它入队时冻结的100张上限。
2. 部署新代码后，同时把上限改为0、白名单清空并把范围设为 `all`。
3. 启动后核对健康接口中 `logistics_write_policy.scope=all` 和 `logistics_write_enabled=true`。
4. 首次手动更新后核对 `selected` 等于全部差异数、`deferred=0`，并检查失败和待核对明细。

本策略只改变每次手动任务的写入数量范围，不启用定时业务同步，也不改变所使用的 `beefun.orderfreight.updatefreight` 接口。
