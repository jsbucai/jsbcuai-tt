# 库存台账与产品主图接口说明 0.3.0

本文说明 UL 随行 0.3.0 的库存台账、库存子集刷新和产品主图实现。本文描述的是数据合同和故障处理规则，不代表任何线上账套的验收结果。

## 1. 范围与基本口径

- 所有订单、库存快照、库存流水和库存子集刷新只处理业务仓库 **08390**。管家婆 API 中使用的内部仓库 ID 为 `29871293290508390`。
- 当前库存以库存 API 的 `qty` 为实物库存、`saleqty` 为可销售库存。采购未到按 `qty - saleqty` 计算。
- 台账用于解释实物库存的历史变化，不用流水伪造历史可销售库存。
- 数量在 SQLite 和 API 中均使用十进制文本，例如 `"12.5"`，计算使用 `Decimal`，不使用二进制浮点数。
- 台账从 `2026-08-07 00:00:00`（上海时区）开始覆盖。更早的数据不在本版本的连续覆盖范围内。
- 服务端不知道尚未上传或尚未过账的手机草稿。历史接口的 `pending_adjustments` 当前固定为空数组，由 Android 将本机 outbox 中的报损、报溢草稿合并到“影响可售、未计入实物台账”提示中。

## 2. 数据模型

数据库迁移版本为 SQLite `user_version=4`。业务查询数据仍保存在现有 `records` 表，新表承担台账和图片状态。

### 2.1 `inventory_movements`

保存从单据中心读取的已过账库存变动明细。

- 稳定身份由账套、`vchcode`、`dlyorder` 和仓库组成；`event_id` 是上述身份的稳定哈希。
- 唯一约束为 `profile_id + source_bill_id + source_line_id + warehouse_id`，同一重叠窗口重复读取不会产生重复流水。
- 商品身份由 `profile_id + warehouse_id + product_id + sku_id + base_unit` 组成，并与已发布的 08390 库存目录关联。
- `raw_quantity` 保存 API 原始数量，`signed_quantity` 保存标准化后的有符号数量；正数表示入库，负数表示出库。
- `document_type_code`、`document_type`、`inout`、`redold`、`redword`、往来单位、摘要和备注用于审计及方向核对。
- `semantics_verified` 表示该行的单据类型、方向和 `inout` 组合是否已经具备可信语义。未验证行可以保存和显示增减量，但不能生成历史余额。
- `source_hash` 用于识别源内容，`sync_token` 标识本次读取批次。

### 2.2 `inventory_snapshots`

保存每个商品/SKU/基本单位的当前库存锚点。

- `physical_quantity` 和 `saleable_quantity` 来自当前库存 API。
- `as_of`、`data_version` 说明库存锚点所属的数据版本。
- `coverage_from`、`coverage_to` 说明台账覆盖窗口。
- `reconciliation_status` 为 `reconciled`、`incomplete` 或 `pending`。
- `reason` 保存不能安全显示余额的原因。

历史余额从当前 `physical_quantity` 向前反推。`reconciled` 表示本系统已连续取得设定窗口内的流水，并且没有已知缺项或未验证方向；它不等同于与某个 2026-08-07 以前的外部期初余额完成独立会计对账。

### 2.3 `inventory_sync_watermarks`

按账套、仓库和来源保存同步水位。

- `last_success_at` 是最近一次成功提交台账窗口的时间。
- `last_full_at` 是最近一次完整核对时间。
- `coverage_from/to` 是累计覆盖范围。
- `status` 表示本次台账是 `succeeded` 还是因缺项而 `incomplete`。
- `payload` 只保存单据数、流水数、问题数和是否完整核对等摘要，不保存密钥或完整 ERP 响应。

### 2.4 `product_images`

每个账套、商品最多保存一张主图的元数据。

- `image_id` 由账套、商品 ID 和规范化源 URL 生成。
- SQLite 保存源 URL、上游 ETag、Last-Modified、内容 SHA-256、长度、MIME、缓存文件名、状态和时间。
- 图片字节保存在 N150 本地 `runtime/product-images` 目录，不写入 SQLite。
- `status` 使用 `pending`、`ready` 或 `failed`。图片缺失或下载失败不阻止订单、商品和库存数据发布。

## 3. 增量同步与完整核对

### 3.1 72 小时重叠增量

正常手动更新从 `last_success_at - 72 小时` 读取到本次更新开始时间，且不会早于 `2026-08-07 00:00:00`。

读取成功后，该重叠窗口被视为权威结果：系统在同一个数据库事务中删除该时间窗内的旧流水，再写入本次完整结果。因此 ERP 中对近期单据的修改、红冲或删除可以在后续更新中得到修正，而不会只追加旧值。

单据中心按 500 单分页读取，并执行以下完整性检查：

- 单据必须有唯一 `vchcode`，明细必须有唯一 `dlyorder`。
- 跨页出现重复身份时，本批不提交。
- 多页读取完成后重新读取第一页；第一页变化表示分页期间源数据发生变化，本批不提交。
- 分页未闭合或超过上限时，本批不提交。

### 3.2 每 7 天完整核对

以下任一条件会从固定基线读取至当前时间：

- 尚无台账水位；
- 尚未成功执行过完整核对；
- 距离 `last_full_at` 已满 7 天；
- 手动更新任务使用 `mode: "reconcile"`。

7 天规则在下一次手动业务更新时触发，不是独立定时任务。完整核对成功后才更新 `last_full_at`。读取或校验失败时不前移水位，也不覆盖上一份可用台账。

### 3.3 与查询发布的关系

订单、库存查询快照与成功的台账批次在同一 SQLite 发布事务中落库，避免同一版本只有半份台账。台账 API 暂时不可用时，订单和当前库存查询仍可发布；此时台账阶段的 `commit` 为 false，旧流水、旧快照和旧水位保持不变。新商品没有可用台账快照时，历史状态为 `pending`，余额为空。

因此，“更新订单成功”与“库存台账已推进”是两个不同结论。客户端应以历史接口的 `status`、`coverage` 和 `reason` 判断余额是否可用，不应只依据更新任务是否发布查询数据。

## 4. 单据类型与余额保护

本版本读取以下单据类型：

| 编码 | 单据类型 | 当前语义保护状态 |
| ---: | --- | --- |
| 34 | 进货入库单 | 已验证类型 |
| 6 | 进货退货单 | 已验证类型 |
| 143 | 进货换货单 | 未验证类型 |
| 11 | 销售出库单 | 已验证类型 |
| 45 | 销售退货单 | 已验证类型 |
| 142 | 销售换货单 | 未验证类型 |
| 21 | 调拨单 | 未验证类型 |
| 9 | 报损单 | 已验证类型 |
| 14 | 报溢单 | 已验证类型 |
| 16 | 生产组装单 | 已验证类型 |
| 139 | 其他出库单 | 未验证类型 |
| 126 | 其他入库单 | 未验证类型 |
| 152 | 内部领用单 | 未验证类型 |
| 153 | 领用退回单 | 未验证类型 |

“已验证类型”仍需每一行满足有符号 `qty` 与 `inout` 的方向关系。关系不一致时，该行自动降为未验证。红冲单保留 API 返回的有符号数量，同时记录红冲标记；不再对所有红字单统一翻转符号。

调拨单会检查第一仓库和第二仓库，只记录 08390 一侧，并按调入/调出确定候选符号。由于当前调拨语义仍列为未验证，即使记录了增减量也不会据此显示反推余额。

只要某个库存身份存在下列任一情况，其快照即标记为 `incomplete`：

- 单据类型或方向尚未验证；
- 流水无法关联当前 08390 商品/SKU；
- 明细身份、数量或结构不完整；
- 本批存在会影响连续覆盖的全局问题；
- 库存子集刷新发现实物库存变化，但对应流水尚未同步。

`incomplete` 状态仍返回流水的日期、单据、往来单位和增减量，但所有 `balance_after` 必须为 `null`，防止把不完整反推结果显示成真实库存余额。

## 5. 库存历史 API

### 5.1 请求

```http
GET /api/v2/inventory/{record_id}/history
Authorization: Bearer <session>
```

`record_id` 是 `GET /api/v2/inventory` 返回的库存记录 ID，不是商品编号或 SKU。接口只接受属于 08390 的已发布库存记录。

### 5.2 截断规则

流水按 `posted_at`、源单据 ID、源明细 ID 倒序返回：

1. 从最新一笔开始；
2. 遇到 `signed_quantity > 0` 计为一次正向入库；
3. 包含第 4 次正向入库所在的记录，然后停止；
4. 总数最多 120 条。

若可用窗口内不足 4 次正向入库，则返回已有记录，最多 120 条。`coverage.positive_inbounds` 表示本次结果实际包含的正向入库次数，`coverage.truncated` 表示仍有更早记录未返回。

当余额允许显示时，最新一笔的 `balance_after` 等于当前实物库存；随后每向前一笔，就从较新的余额中减去该笔 `quantity`。当状态不是 `reconciled` 时，不执行这项余额展示。

### 5.3 响应结构

```json
{
  "ok": true,
  "record_id": "库存记录ID",
  "product": {
    "profile_id": "账套ID",

    "product_id": "商品ID",
    "sku_id": "SKU内部ID",
    "base_unit": "1",
    "sku": "商品编号",
    "product_name": "商品名称",
    "unit_name": "件"
  },
  "snapshot": {
    "physical_quantity": "70",
    "saleable_quantity": "60",
    "as_of": "带时区时间",
    "data_version": "数据版本"
  },
  "status": "reconciled",
  "coverage": {
    "from": "覆盖开始时间",
    "to": "覆盖结束时间",
```

接口故障语义：记录不存在或不属于 08390 返回 HTTP 404；请求参数无效返回 HTTP 400；数据库或未处理的服务错误返回 HTTP 500。`status: "incomplete"` 是正常的安全响应，不是 HTTP 错误。

## 6. 报损报溢后的库存子集刷新

局域网电脑建立 ERP 报损、报溢草稿后，Android 可以请求 N150 只刷新受影响商品：

```http
POST /api/v2/update-jobs
Authorization: Bearer <session>
Content-Type: application/json

{
  "id": "客户端生成的UUID",
  "mode": "inventory_subset",
  "product_ids": ["商品ID"]
}
```

也可以在 `request` 中传 `product_ids`，或传包含 `warehouse_id`、`product_id` 的完整 `identities`。一次必须包含 1 至 100 个商品，并且仓库只能是 08390。

子集刷新具有以下边界：

- 只读取并更新已经发布的 08390 库存行；不创建新商品，不写 ERP，不执行物流更新。
- 必须完整闭合分页、账套、仓库、商品和 SKU 范围，且发布期间完整数据版本没有变化，才在一个事务中更新 `qty/saleqty`。
- ERP 没有返回某个已发布 SKU 时，将其本次库存视为零；ERP 返回范围外或重复 SKU 时整批拒绝。
- 同一 UUID 和同一冻结请求是幂等重放。相同 UUID 携带不同请求会被拒绝。
- 若另一个不同更新任务正在排队或运行，返回 HTTP 409 `update_busy`，不会把本次草稿变化静默并入旧任务。
- 仅可销售库存变化时保留原台账核对状态。实物库存变化时把对应快照标记为 `incomplete`，原因是“实物库存已变化，等待单据流水同步核对”；下一次台账同步后再恢复可信余额。

## 7. 产品主图缓存与 API

### 7.1 元数据同步与来源限制

商品主数据同步时读取 `picurl`，每个商品最多保留一张主图。源 URL 必须满足全部条件：

- 主机严格等于 `erp.qiniu.wsgjp.com`；
- 只接受 HTTP 或 HTTPS，并统一规范为 HTTPS；
- 不允许用户名、密码、非标准端口、反斜杠路径或跳转；
- 下载前 DNS 解析结果必须全部是可用公网地址；
- 只接受 PNG、JPEG 或 WebP，且同时校验响应 MIME 与文件魔数；
- 单张图片最大 12 MiB。

图片请求不携带管家婆 Token、Cookie 或其他 ERP 凭据。源 URL 只保存在服务器数据库中，不返回给手机。

### 7.2 图片列表

```http
GET /api/v2/products/{product_id}/images
Authorization: Bearer <session>
```

`product_id` 是 ERP 商品内部 ID。无图片时返回 HTTP 200 和空 `items`；有图片时返回零或一项：

```json
{
  "ok": true,
  "product_id": "商品ID",
  "items": [
    {
      "id": "图片ID",
      "product_id": "商品ID",
      "content_url": "/api/v2/product-images/图片ID/content",
      "mime_type": "image/png",
      "width": null,
      "height": null,
      "etag": "上游ETag或内容SHA-256",
      "updated_at": "发现或下载时间"
    }
  ]
}
```

图片尚未首次下载时，`mime_type`、尺寸和 `etag` 可能为空。列表中的 `etag` 是元数据提示；缓存下载和 HTTP 条件请求应以内容接口实际返回的 `ETag` 响应头为准。

### 7.3 图片内容与 ETag

```http
GET /api/v2/product-images/{image_id}/content
Authorization: Bearer <session>
If-None-Match: "上一次内容响应的ETag"
```

第一次访问时按需下载，并通过临时文件、`fsync` 和原子替换写入缓存。每次使用缓存前都会核对文件长度和 SHA-256；损坏或缺失的缓存不会直接返回。

内容响应的 HTTP `ETag` 使用本地文件的 SHA-256，与上游厂商 ETag 解耦。匹配 `If-None-Match` 时由 HTTP 层返回 304；成功内容响应带 `Cache-Control: private, max-age=86400`，避免公共代理共享登录后的业务图片。

商品目录再次发现同一 URL 后，下一次打开图片会使用已保存的上游 `ETag` 和 `Last-Modified` 发起条件校验。上游返回 304 时继续使用本地缓存；内容变化时原子替换文件并生成新的内容 ETag。商品 `picurl` 改变时会生成新的图片身份、清空旧元数据的可用状态并重新下载，旧内容不会继续作为该商品主图返回。

### 7.4 图片故障语义

- 图片 ID 不存在：HTTP 404 `not_found`。
- 来源、DNS、大小、格式或上游响应不符合要求，且没有有效旧缓存：HTTP 502 `image_unavailable`。
- 上游暂时失败但本地旧缓存的长度和 SHA-256 仍有效：返回旧缓存，保证商品查询可用。
- 下载失败会记录 `failed` 和简短错误；后续内容请求仍可重试。
- 图片失败不回滚订单、商品或库存查询快照。

## 8. 备份与恢复边界

`inventory_movements`、`inventory_snapshots`、`inventory_sync_watermarks` 和 `product_images` 元数据属于 SQLite 一致性备份范围。恢复后必须保留它们与 `records`、`settings` 的同一数据版本关系。

图片字节缓存可以重新下载，不是业务恢复的必要数据。恢复后若元数据中的缓存文件不存在或校验不通过，内容接口会重新获取；在重新获取成功前不会把无效文件返回给手机。
