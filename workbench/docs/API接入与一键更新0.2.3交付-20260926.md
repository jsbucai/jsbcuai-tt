## 实际 API 读取依据

| 数据 | 当前实现与边界 |
|---|---|
| 未发货清单 | `qimen.taobao.erp.order.sync`，1900–2100、状态 1–5、每页 100；按原始页数闭合，仅完全相同重复记录可合并。其返回的 `TotalResults` 是总数，`totalResults` 是本页数；已修复响应格式适配。此清单不是已验证的全部销售剩余需求。 |
| 摘要及可靠明细 | `erp.ewms.stockoutbill.query`，实测使用小写 `numbers/status`；按请求订单逐笔匹配。部分旧订单没有详情或没有摘要，明确保留缺项。文档中的大写参数实测失败；不使用返回范围异常的 `vchcodes` 筛选。 |
| 商品与库存 | `erp.ptype.list`、`erp.stock.list`、`erp.goodsstocks.list` 全分页，显式按商品批次和仓库读取。库存键包含账套、仓库、商品、SKU、基本单位代码，SKU 使用实际返回的 `skuid`。 |
| 数量口径 | 库存数量=`qty`，可销售库存=`saleqty`，采购未到总量=`qty-saleqty`，包括改制；订单展示的是 API 原销售数量，未将其填入 `open_qty`。 |
| 单位与仓库 | 只有唯一对应的 WMS 商品明细及已核实基本单位才建立订单与库存关联；名称空保持空，不虚构“件”。无法唯一匹配的单位、仓库和明细标记未知。 |
| 进货历史 | `erp.bill.billcenterlist`，近 180 天已过账入库、退货及换货，保留红冲标记。用于历史查询，不作为未到采购批次。按过账日期声明覆盖范围，越界查询返回 422。 |

公开接口文档：[管家婆 API 文档](http://d7safe.mygjp.com.cn:8020/web/#/erpapi/509)。本次保留的只读字段证据见开发工作区 `reports/qimen-envelope-mapping-20260926.json`；客户原文及密钥不包含在交付源码中。

## 尚未解除的上线限制

1. 没有经过真实单据验证的销售交货日期字段，因此不会从旧物流单号、创建时间或当前日期推算目标日期。
2. 部分完成、终止、关闭与剩余未完成数量尚未建立完整 API 映射。当前销售数量不能参与库存分配；需要对照全部未结束需求，而不只是最近 180 天导出样例。
3. 采购及改制的日期、供应商与剩余批次未完整读取；库存差额只能提供总量，不能提供催货依据。
4. 实际到货与退货、红冲及原分配账本的身份转换尚未闭环，不能重置账本重复分配。
5. 旧单摘要未全部补齐，买家账号字段大多为空。当前可按商品、完整订单号和已取得的摘要查询；买家查询覆盖尚不完整。

因此本次所有订单均暂停物流计算写回，`UL_LOGISTICS_WRITE_ENABLED=0`；ERP 物流逐笔请求记录为 0。候选写入只允许 `beefun.orderfreight.updatefreight`，明确排除触发发货的 deliver 接口。完整分类算法、异常关联传播、缓存差异、未知结果与恢复流程已在测试数据上接通；这不能替代真实业务字段验收。

继续工作需要原电脑按 NAS 根目录的 `API字段补充请求-20260926.md` 提供实证。没有可用 API 时请明确说明，需要进一步确认 ERP 能力；不采用 Windows 页面导出作为 N150 长期运行依赖。正式打开物流写入前，还需完成近期单笔、小批量验证，并停止旧电脑并行修改同一物流字段。
