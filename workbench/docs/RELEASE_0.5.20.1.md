# 0.5.20.1：存储维护与重任务串行

2026-10-12，已部署 `ul-workbench:0.5.20.1-storage`。Android 保持现有版本，不需要重新安装。

## 已查明的增长来源

发布前根分区总容量约 16.7 GB，使用率 83.7%，可用约 2.72 GB。数据库约 602 MB；其中旧物流计算快照占约 304 MiB，历史诊断问题占约 45 MiB。迁移数据库副本约 2.4 GB，NAS 中还有多次发布形成的同日重复备份。

任务事件中已有超过十万条 `source_updated`。原实现仅因读取时间或数据版本改变，也会逐任务追加一条更新事件，实际业务内容可能并未改变。

## 已实施的控制

1. **任务事件去重。** 新来源版本仍推进任务版本和选择冲突检查，但单纯来源时间变化不再追加业务事件。负责人、状态、内容、人工操作等真实变化继续留痕，旧事件不删除。
2. **旧计算结果归档。** 保留每个账套最近六批、最近两小时、当前来源及任务投影引用的计算；仍运行、结果不明、物流占用或等待任务投影恢复的批次固定保留。其余计算快照、旧诊断问题先加密压缩到 NAS，校验成功后才释放数据库内容，保留归档引用。更新任务结果、物流尝试和范围不删除。
3. **数据库副本迁出系统盘。** 迁移备份保留最新两份；较旧静态副本检查完整性、无活跃 WAL，并经加密归档、解密散列验证后迁至 NAS。归档恢复只能写入一个不存在的新文件，不能覆盖在线数据库。
4. **备份轮换。** 保留最新三份、最近 30 天每天一份、八周每周一份、十二个月每月一份，并额外保留近期发布检查点。清理前要求存在 48 小时内成功备份，并实际解密及校验压缩包完整性。NAS 未挂载、验证失败时不清理。
5. **缓存及日志。** 商品图片缓存目标 512 MiB，仅清理孤立文件或至少七天未使用的可重新下载文件，商品元数据、订单附件不删除。系统日志上限 128 MiB、最长 14 天；容器继续沿用三份、每份 10 MiB 的限制。计算归档及维护报告保留 90 天；旧数据库归档长期保留。
6. **统一重任务占用。** API 更新、历史回填及任务投影恢复加入现有浏览器/OCR/Codex/商品创建共用的文件锁，夜间维护也使用同一把锁。繁重任务顺序执行，普通 App 查询不加入这条执行队列。
7. **空间不足保护。** 保留至少 1 GiB，或数据库大小两倍加 256 MiB（取较大值）的余量。低于余量时自动更新保留原队列任务并延后，不继续下载；新附件上传明确提示空间不足。已有数据、幂等回执和待核对操作保留。

这是冗余数据和重任务控制，不是删除历史订单。人工处理、负责人、打印、纠正、录单及采购事实继续长期保存，会随真实业务增长；NAS 旧数据库归档也会缓慢增长，不能据此声称存储永远不需要扩容。

- 08:00–18:45：每 15 分钟自动更新，沿用 0.5.20 的有界重读、同任务恢复及物流差异写入规则。

## 归档恢复

在 N150 的 `/opt/ul-workbench/service` 下，使用受限备份密钥验证并解密到一个新的路径：

```sh
/opt/ul-sales-runner/venv/bin/python -m core.maintenance_archive \
  /mnt/nas/开发项目/UL随行/冷归档/旧数据库副本/需要恢复的文件.ulcold \
  /一个不存在的临时路径/恢复.sqlite3 \
  --key-file runtime/data/secrets/backup.key
```

先在隔离环境核验用途和版本，不将该文件直接覆盖到在线数据库。密钥不包含在 NAS 普通交付包或 APK 中。
