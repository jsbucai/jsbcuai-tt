# ERP物流小批量写入安全审计（2026-10-02）

实施版本：后端 `1.4.6`／镜像 `0.4.6`。

## 结论

原实现不能直接通过打开 `UL_LOGISTICS_WRITE_ENABLED=1` 上线。Android 的“更新订单”固定提交 `mode=sync`，而后端把 `sync` 和 `update` 都视为可写模式。首次没有 `freight_cache` 时，全部差异候选会按订单号逐笔调用 `beefun.orderfreight.updatefreight`；当前预览约有两千三百余条候选，原代码没有每任务上限或订单白名单。

本次已在本地代码加入服务器端双重边界，但没有部署、没有调用 ERP：

- 全局开关只启用 ERP 写入传输，不再单独构成写入授权。
- `UL_LOGISTICS_WRITE_MAX_PER_JOB` 提供每个持久任务的有限上限。
- `UL_LOGISTICS_WRITE_ALLOWLIST` 提供完整订单号白名单；同时配置时先筛白名单，再应用上限。
- 两项边界都未配置时，即使全局开关为1，也返回 `policy_blocked`，发送数量为0。
- 策略在任务入队时写入任务记录；服务重启或修改 `.env` 不会放宽已经排队的任务。
- 结果分别记录 `selected`、`deferred`、`unchanged` 及订单号。因上限或白名单未发送的订单属于 `deferred`，不会伪装成 `unchanged`。
- 成功项才进入 `freight_cache`。下次任务跳过缓存命中的目标，从剩余差异中继续选择下一批。

## 建议上线顺序

1. 先以全局开关0部署代码并核对健康接口显示物流写入关闭。
2. 选择3张相互独立、交期和物流公司均明确、可在 ERP 页面立即复核的订单。
3. `.env` 设置全局开关1、上限3、白名单为这3个完整订单号，重启服务后运行一次真实 `sync`。
4. 核对任务只有3个 `freight_attempts`，再在 ERP 页面逐单确认公司、单号以及发货/记账状态没有变化。
5. 验收成功后清空白名单，保留每任务上限100。每次手动“更新订单”最多处理100个新差异；不要取消上限。
6. 任意请求进入 `unknown` 时停止继续批次，先人工核对并通过现有确认接口处理。

Compose 会自动从同目录 `.env` 读取三项配置；安全模板见 `.env.example`。真实 `.env` 继续排除在交付源码和备份报告之外。
