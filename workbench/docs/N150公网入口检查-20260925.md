# N150 公网入口检查

检查时间：2026-09-25 晚间。此文件只记录网络诊断，不表示 UL 业务已经部署或可上线。

后续状态：2026-09-26 已完成 DNS、独立证书、8443 入口及后端部署，用户手机登录成功，详见 `N150公网部署与0.2.2交付-20260926.md`。以下内容保留为部署前的诊断记录。

## 已核实

- 向阿里云权威 DNS `dns27.hichina.com` 查询 `ul.yingyinghome.com`，得到带权威标志的 NXDOMAIN；UL 子域名尚未建立。没有用本地代理 Fake-IP 判断公网解析。
- `yingyinghome.com` 权威 A 记录为 `153.34.4.88`，与本次观察到的家庭 WAN 地址一致；此地址可能随拨号变化。
- iStoreOS 当前生效的 WAN TCP 80、443、8443 均转发到 `192.168.100.30` 的同号端口。
- `.30` 是 Proxmox CT 102（hht-call），运行 Caddy 和原家庭应用。Caddy 监听 80、443、8443；443 与 8443 的站点域名均为 `yingyinghome.com`，业务反代为 `127.0.0.1:8080`。
- 从家庭网络直接访问 `.30` 并使用正确域名/SNI：443、8443 均返回 HTTP 302，TLS 证书校验通过。80 返回 HTTPS 跳转。
- 当前证书 SAN 仅包含 `yingyinghome.com` 与 `www.yingyinghome.com`，不包含 `ul.yingyinghome.com`。不能直接把该证书当作 UL 子域名证书。
- 未发现 UL 后端 5191 监听，也未创建计划中的 UL Debian 虚拟机。当前 APK 默认地址不能连接的直接原因包括域名缺失及服务未部署。
- 路由器自身 uhttpd 监听 443/8443，但公网流量已经由 DNAT 转发到 `.30`；这一现象本身不构成端口冲突。本次未发现 Caddy 重复绑定失败。

## 公网实测结果

- 本机默认路由经 `utun4` 家庭 VPN；从本机访问家庭 WAN 地址不能作为独立公网测试。
- 检查时 8443 转发计数非零，80/443 计数为零。计数不能单独证明运营商封禁。
- Check-Host 外部探测接口因当前访问链路 TLS/连接失败，未得到有效远端检测结果。网页抓取工具失败同样不能作为封禁依据。
- 用户已通过手机关闭 Wi-Fi 与 VPN，仅使用移动数据对照访问原家庭站点，确认 **8443 能打开，443 打不开**。
- 结合内部 443/8443 均正常、WAN 转发规则已生效，故障范围已缩小到 443 的公网访问路径；符合运营商端口过滤的表现，但本次没有运营商侧证据证明过滤的具体位置。

## 入口决策

1. 根据本次移动网络实测，UL 后续部署地址确定为 `https://ul.yingyinghome.com:8443`；App 支持显式 HTTPS 端口。
2. 当前已交付的 0.2.1 APK 默认地址仍不带端口，部署完成时需同步调整默认地址及用户已保存的服务器地址。此次诊断没有重新发布 APK，也没有把尚未部署的地址标记为可用。
3. 不依赖公网 443，不将问题归因为“家庭网页占端口”。
4. 复用现有 Caddy 的域名路由即可共用入口；当前没有必要停家庭网站。不能停止整个 Caddy 来为 UL 让端口。
5. 部署时仍须建立 UL DNS/DDNS、申请覆盖 UL 域名的证书及续期机制、添加 Caddy 路由、启动独立后端并完成管理员初始化。若 80/443 被过滤，证书申请优先考虑 DNS 验证，不能假设 HTTP/TLS 端口验证可用。
6. 后端 5191 仅在内网向代理开放，不直接转发公网。完整 API 数据映射和业务验收继续按迁移计划执行。

本次未修改 DNS、防火墙、端口转发、Caddy 或现有网站；未进行 ERP 写入。
