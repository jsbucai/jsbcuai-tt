# 0.5.20：更新稳定性、采购采集暂停与工作时段同步

2026-10-12。后端兼容更新，Android 保持 0.4.13-dev。

## 查证与决策

- 11:30 自动刷新和 14:03 手动更新都因需结存订单复核中断，最后成功来源仍为 08:13。实时双读得到同样的 55 张订单，内容完全一致，只是排列不同；原代码对整个有序数组做比较，造成误报。
- 11:22 的普通订单分页确有总数变化。不能删掉完整性校验：只重读受影响来源，仍不得发布拼接不完整或身份冲突的数据。
- 采购网页自 10 月 9 日起等待人工登录验证，后续时段仍积累下载任务并堵住网页通道。已按用户要求暂停采购网页采集和定时触发，保留原快照及原失败、暂停记录。
- N150 业务虚拟机只有约 2 GB 内存；本次观察空闲负载约 0.02、可用内存约 913 MB、API 容器约 771 MB。使用串行和合并请求，不在此机器上增加同步并发。

## 已实现

1. 需结存及库存/进货流水的分页复核忽略单据排列，但保留所有业务字段及重复项。真实内容变化仍需重读。
2. 订单、商品/库存分页及进货流水发生数量变化、重复或未闭合时，当前来源最多读三次。仍不稳定时，同一更新任务持久保留，30 秒起退避到最多 5 分钟续读；不重复创建更新，不发布半份数据。缺少身份、字段合同错误等真实问题仍明确报错。
3. 自动任务沿用已启用的服务器物流写入策略并冻结到每次任务。查询与分类先发布，再按原差异缓存写物流；不重复写相同目标。未知结果继续保持原占用和核对边界，不因本次重读机制重复写入。
4. API 更新与实际网页操作在 SQLite 同一写事务下互斥领取，避免两者同时抢资源。已中断销售导入的本地回执恢复仍可单独处理，不接触 ERP。
5. 采购登录/验证失败即暂停采集，撤下只读下载积压；销售和采购写入单据不受此取消逻辑影响。采集超过十分钟也暂停，结束隔离子进程；恢复后只接收新任务，不补跑旧时段。登录凭据与采购原快照均不修改。

## 验证与边界

- 246 项相关回归通过；包括来源重排、单次变动恢复、持续变动有界重读、退避任务继续使用原物流范围、夜间边界、触发合并、采购暂停不取消销售、读写队列互斥、打印/订单生命周期回归。
- 新镜像只读实测读取当时 58 张需结存订单成功，耗时 1.66 秒，无 ERP 业务写入。
- 发布前后 NAS 一致性备份；短暂关闭新打印准备且确认无活跃打印任务，程序升级前后受保护业务事实散列一致。健康恢复后立即恢复打印。
- 这不是全量历史重建，也没有实现跨页数据库快照隔离：持续变动会延后到稳定窗口，App 保留上次完整数据和真实成功时间。
- 目前一次完整更新约 3–4 分钟，15 分钟触发在无持续源变化/长网页操作时可将正常可见延迟控制在约 15–20 分钟；这不是保证值。大批历史补齐仍在低峰处理。尚未声称真机 p95、长期吞吐或持续三日运行已验收。
- OCR、Codex 的独立执行器保持原逻辑；若后续并发使用增长，需进一步统一重任务调度并评估增加 VM 内存，不能靠同时启动更多进程提速。

证据目录：`outputs/update-reliability-20261012/`。自动物流没有放宽原有商品身份、客户归属、缺交期和结果不确定的限制。回退程序时保留新同步、物流及人工事实，不覆盖旧数据库。
